# HITTER / RobotBridge2_20260721_2109 关键理解记录

## 1. RobotBridge2_20260721_2109 相比 RobotBridge2 的变化

`RobotBridge2_20260721_2109` 不是简单改名，而是把 HITTER 的 MuJoCo 部署侧做了更完整的乒乓球运行化改造。

### 1.1 默认仿真从 real_world 变成 mujoco

`RobotBridge2` 的 HITTER 配置默认更偏 `real_world`，而 `RobotBridge2_20260721_2109` 的 `hitter.yaml` 默认已经是：

```yaml
sim: mujoco
sim.config.table_tennis.enabled: true
sim.config.table_tennis.physics_mode: mujoco
sim.config.table_tennis.continuous_ball_launcher: true
```

也就是说，`new` 版本开箱就偏向 MuJoCo 乒乓球演示。

### 1.2 增加了更完整的 table tennis 配置

`RobotBridge2_20260721_2109/deploy/config/sim/mujoco.yaml` 里新增了很多球相关参数，例如：

```text
physics_mode
continuous_ball_launcher
randomize_ball_on_reset
ball_initial_pos / ball_initial_lin_vel
launcher_x_bounds / launcher_y_bounds
landing_target_w
use_analytic_table_bounce
use_analytic_racket_hit
```

这说明 `new` 版本已经把球路、连续发球、reset、出界判断和落点目标都配置化了。

### 1.3 HitterEnv 新增了 planner 重试和命令锁定相关逻辑

`RobotBridge2_20260721_2109/deploy/envs/hitter.py` 新增了这些行为：

```text
update_command_while_armed
ball_planner_replan_attempts
racket_velocity_clip
hitter_debug_metrics
```

含义是：

- planner 失败时可以重试
- armed 后默认不在每帧刷新命令
- 球拍速度会被裁剪到训练范围
- simulator 的球状态统计会回传给 env

### 1.4 MuJoCo simulator 增强了球物理和统计

`RobotBridge2_20260721_2109/deploy/simulator/mujoco.py` 里加入了：

```text
physics_mode = mujoco / analytic / hybrid / analytic_kinematic
continuous_ball_launcher
hit_count / landing_count / miss_count
ball_age_s
table/racket contact 检测
```

所以 `new` 版本更像“连续发球 + 球状态统计 + 多种球物理模式”的实验版。

### 1.5 XML 里打开了球和球拍的真实接触

`RobotBridge2_20260721_2109` 的 MuJoCo XML 里，球和球拍碰撞几何都打开了 contact：

```text
hitter_ball_geom contype="1" conaffinity="1"
right_racket_face_collision contype="1" conaffinity="1"
```

这和旧版更依赖解析击球逻辑的做法不一样。`new` 版本更偏向让 MuJoCo 真接触来跑球。

### 1.6 去掉了 playback_slowdown

旧版 `RobotBridge2` 里有：

```yaml
playback_slowdown: 1.0
```

`RobotBridge2_20260721_2109` 里没有这个字段，所以不能再用旧版那种慢放参数。

### 1.7 real_world 球跟踪更稳

`RobotBridge2_20260721_2109/deploy/simulator/real_world.py` 还补了：

```text
ball_message_timeout_s
ball_timeout_warn_period_s
stale ball tracking cleanup
```

这让真实世界 Vicon 球消息断掉时不会一直拿旧状态继续算。

### 1.8 一句话总结

可以把两者理解成：

```text
RobotBridge2：更偏单次击球/解析辅助/观察验证
RobotBridge2_20260721_2109：更偏连续发球/真实 MuJoCo 球物理/球状态统计
```

## 2. tts 的含义

`tts` 是 `time to strike`，意思是“距离计划击球时刻还剩多久”。

它不是仿真从初始时刻开始经过了多久，而是：

```text
tts = 预测击球时刻 - 当前时刻
```

例如日志里：

```text
tts=0.806s
```

表示 planner 判断这一次击球大约还要 0.806 秒才到击球点。

## 3. tts 为什么之前是 0

当 `physics_mode=mujoco` 时，球第一次碰到桌面后容易沿桌面滚动，球状态会偏离 planner 的预期。

这会导致 planner 看到的球路不稳定，甚至认为：

```text
球已经到达击球平面
```

于是 `tts` 会被压到 `0.000s`，也就是“现在就得打”或者“已经错过击球窗口”。

## 4. 为什么 `analytic_kinematic` 更正常

运行：

```bash
python run.py \
  --config-name=hitter \
  sim.config.table_tennis.physics_mode=analytic_kinematic \
  mimic.motion.ball_planner.prediction_horizon_s=4.0
```

后，球路正常的原因主要有两个：

### 3.1 球物理更稳定

`analytic_kinematic` 下，球不再完全依赖 MuJoCo 的自然接触来处理桌面反弹和球拍击球，而是用解析逻辑推进：

- 桌面反弹按 restitution 处理
- 球拍命中按目标点直接给出出球速度
- 球不会轻易贴桌滚动

### 3.2 预测窗口更长

`prediction_horizon_s=4.0` 让 planner 有足够时间往前看，能更稳定地算出：

- 球什么时候过击球平面
- `tts` 应该是多少
- base target 和 racket target 应该放在哪里

所以 `tts` 会回到一个正常的倒计时范围，比如 `0.78s ~ 0.88s`。

## 5. 一次击球会生成几次 command

默认情况下，**一次击球只生成一次 command**。

当前配置里：

```yaml
update_command_while_armed: false
```

所以流程是：

```text
1. 当前没有命令
2. planner 生成一次 HITTER command
3. command 被 armed 并锁定
4. policy 按这一次 command 准备击球
5. 击球窗口结束后，再进入下一球
```

`ball_planner_replan_attempts=4` 不是“一拍生成 4 个 command”，而是 planner 失败时最多重试 4 次，最终仍然只会 armed 一个命令。

## 6. 结论

可以把当前现象理解成：

```text
physics_mode=mujoco
-> 球接触不稳定
-> planner command 不稳定
-> tts 贴近 0
-> policy 很难打好

physics_mode=analytic_kinematic + 更长 prediction_horizon
-> 球路稳定
-> planner command 稳定
-> tts 合理
-> policy 更容易打出来
```
